# excelrs — Design Reference

**Package:** `@levu304/excelrs` (Rust port of ExcelJS 4.4.0 to a Node.js native addon)

## What this file is, and what it is not

**This file carries no observable behavior.** It records *why* the system is shaped the way
it is: platform and FFI constraints, crate and module architecture, and decisions that a
specification cannot express.

| If you want to know... | Read |
| --- | --- |
| What the system does | `openspec/specs/*` — the behavior contract, CI-gated |
| Why it is shaped this way | **this file**, and `docs/adr/` |
| What shipped, and when | `CHANGELOG.md` |
| Feature-area status and priorities | `ROADMAP.md` |

**Why the split.** This file previously described the v1.0.0 architecture and API surface
and was never rewritten for v2.x. That made it a second normative surface: it made claims
the code also makes, so it could contradict the code, and nothing checked it. Two
requirements were found asserting things the code contradicted, in the same week, precisely
because nothing verified the prose. The behavior now lives in one CI-gated place.

**A note on the two most-recently-added platforms.** Earlier versions of this file, and two
now-retired capability specs, enumerated which platforms shipped. That is a stale
inventory — it goes false the next time a target is added, and no validator can catch it.
The target list lives in `.github/workflows/release.yml`, and the `platform-targets`
capability states agreement with it as an invariant.

## 1. Design principles

Non-negotiable, and each traced to the decision that carries it.

**P1 — Drop-in API compatibility.** The TypeScript public API mirrors ExcelJS. Method
names, signatures, and the conceptual model (Workbook → Worksheet → Row → Cell) stay
identical, so a user swaps `require('exceljs')` for `require('@levu304/excelrs')` with
minimal code changes. Divergences are permitted where ExcelJS behavior is a defect, and
each must be justified and documented. See [ADR-001].

**P2 — Rust core, JS glue as a mechanical adapter.** All logic lives in Rust. The
TypeScript layer is generated by napi-rs `#[napi]` annotations. A hand-maintained JS glue
file exists solely for napi-rs impedance mismatches — method overloading and optional type
narrowing — and is never business logic.

*The original principle was "no hand-written JS wrappers". The pre-implementation review
found that impossible for two concrete reasons, and the principle was rewritten rather than
the code:* napi-rs v3 supports only C-style enums via `#[napi(string_enum)]`, so `CellValue`
must be a flat `#[napi(object)]` struct with a discriminant string ([ADR-011]); and napi-rs
does not support method overloading, so `getCell(address)` and `getCell(row, col)` must be
two Rust methods behind a JS dispatch ([ADR-012]).

**P3 — Async-native.** Read/write I/O is async Rust on Tokio, exposed as native Promises —
no thread-pool blocking, no callback APIs. See [ADR-004].

**P4 — Fail loudly, fail early.** Every error is a typed `ExcelrsError` variant surfaced as
a descriptive JS `Error`. When parsing fails the entire operation errors; partial data is
never returned.

**P5 — Correctness over features.** XLSX round-trips — write excelrs, read ExcelJS, and
vice versa — must pass before a release. Every feature has a test ported from the ExcelJS
suite.

**P6 — ~~Monolithic until complexity demands otherwise.~~** *Superseded.* The original
threshold was ~5K LoC; the crate is 26,258 and the split lever no longer fit the codebase
shape. Replaced by a file-size trigger. See [ADR-002].

## 2. Crate architecture

### 2.1 Layout

One crate, `excelrs-core`, built as a `cdylib`.

```
src/
├── lib.rs              napi-rs entry point, #[napi] exports
├── model/              20 files — in-memory types; the single source of truth
│                       for both read and write paths
│   ├── cell.rs         Cell, CellValue (flat #[napi(object)], ADR-011)
│   ├── style.rs        Style aggregate + five sub-types; FillKind, validation
│   ├── color.rs        ThemeColorScheme, ARGB/RGB, tint
│   ├── worksheet.rs    largest file — known debt, see ADR-002
│   ├── workbook.rs     public Workbook
│   ├── workbook_inner.rs  interior-mutable core, behind the handle
│   └── ...             row, column, table, image, comment, defined_name,
│                       data_validation, conditional_formatting, header_footer,
│                       page_setup, sheet_protection, sheet_view, workbook_view
├── reader/             4 files — calamine-backed in-memory XLSX read
│   ├── xlsx.rs         calamine → model translation; 3-pass (values, styles,
│   │                   formulas); largest reader file
│   ├── styles.rs       xl/styles.xml → StyleTableRead; cellXfs index → Style
│   └── workbook.rs
├── writer/             3 files — OOXML emission via zip + quick-xml
│   ├── xlsx.rs         model → OOXML
│   └── styles.rs       style dedup + xl/styles.xml (build_style_table and the
│                       byte-identical incremental StyleAccumulator, ADR-027)
├── formula/            3 files — opt-in formula evaluation (ADR-009)
│   ├── bridge.rs       xlstream value types → CellValue
│   └── tests.rs
├── xlsx/
│   └── handle.rs       lock-free workbook handle: parse outside the lock,
│                       take the lock only to swap state
├── stream.rs           SAX streaming reader/writer
├── stream_handle.rs    streaming workbook state
├── stream-bridge.ts    JS side of the streaming bridge
├── csv.rs              hand-rolled RFC 4180 reader + writer
├── error.rs            ExcelrsError (thiserror)
└── types.rs            shared utilities (address parsing)
```

`index.js` is hand-maintained glue ([ADR-012]). `index.d.ts` and `native.d.ts` are
napi-rs-generated. `stream-bridge.ts` is compiled to `stream-bridge.js`.

### 2.2 Data flow

**In-memory read:**

```
.xlsx file (or Buffer)
  → calamine::open_workbook_auto_from_rs
  → calamine parses OOXML into Sheets/Rows/Cells
  → three passes, merged by cell address:
      values   (rows)                    → cell data        [ADR-015]
      styles   (per-sheet s-index map)   → resolved Style
      formulas (worksheet_formula)       → Cell.formula
  → #[napi] serializes model types → JS objects
```

The three-pass split is not incidental: calamine stores formulas in a separate API from
cell data, so a reader written against `rows()` alone silently turns every formula into its
cached value. See [ADR-015].

**Streaming read/write:** hand-rolled SAX, no runtime calamine dependency. calamine is
retained in `src/stream.rs` as a *documented behavioral oracle* — the shared-formula
reference translation is ported from calamine 0.35.0 and unit tests mirror its behavior so
the two paths can be compared. See [ADR-003].

**Write:**

```
User builds a Workbook in JS
  → model types hold all state
  → writer::xlsx traverses the model
  → style table built (dedup numFmts/fonts/fills/borders → cellXfs index,
    BTreeMap-keyed on canonical serialized form, ADR-027)
  → quick-xml emits OOXML fragments
  → zip assembles the archive
  → Buffer to JS
```

### 2.3 Why these dependencies

| Crate | Why | Alternative rejected |
| --- | --- | --- |
| `calamine` 0.35 (`dates`) | Battle-tested XLSX read; resolves shared strings, date systems, malformed files | Hand-rolling the read path: ~2x the work, more bugs ([ADR-003]) |
| `zip` + `quick-xml` | Full control over emitted OOXML | calamine's writer: insufficient output control ([ADR-003]) |
| `thiserror` | Ergonomic error enum derivation | Manual `Display`/`Error` impls: boilerplate |
| `serde` + `serde_json` | Testing/debugging; the `serde-json` napi feature coerces JS values to Rust | — ([ADR-013], [ADR-026]) |
| `chrono` | Excel serial date handling | `time`: less Excel-date aware |
| `tokio` | napi-rs is Tokio-native | `async-std`: fights the FFI layer's assumptions ([ADR-004]) |
| `napi` + `napi-derive` v3 | Bindings | `neon`: different API surface ([ADR-014]) |
| `futures-core` | Stream plumbing for the streaming path | — |
| `xlstream-parse`, `xlstream-core` | Formula parsing and value types | `formularizer-eval` was **yanked from crates.io**; see `docs/formula-engine-research.md` |

The last two are **optional**, gated behind the `formula-eval` Cargo feature and absent
from default builds ([ADR-009]).

## 3. FFI constraints

These are properties of napi-rs and Node, not choices. They are the reason several designs
look the way they do.

**A Rust enum with variant data cannot cross the FFI boundary.** napi-rs supports only
C-style enums via `#[napi(string_enum)]`, which carry no payload. `CellValue` is therefore
a flat `#[napi(object)]` struct: a `value_type: String` discriminant plus an `Option<T>`
field per variant, only one of which is meaningful. Every read and write branches on
`value_type`; that branch is centralized in one place rather than at each call site.
See [ADR-011].

**Method overloading is not expressible.** `getCell(address: string)` and
`getCell(row, col)` cannot be one `#[napi]` function. They are two Rust methods
(`get_cell_by_address`, `get_cell_by_rc`) behind a JS dispatch in `index.js`.

*Known sharp edge, unfixed:* `ws.getCell(1)` — a single numeric argument — routes to
`getCellByRC(1, undefined)`, where `undefined` coerces to `0`. The second-pass review
recommended an explicit error. See [ADR-012].

**Setters that accept a union take `serde_json::Value`.** The napi v3 `serde-json` feature
auto-converts JS primitives; a union-typed setter has no single Rust parameter that covers
number, string, boolean, `null`, `Date`, and object. Rust branches on JSON shape. Used for
both `cell.value` ([ADR-013]) and `cell.style` ([ADR-026]).

**v3 attribute spellings differ.** `#[napi(constructor)]` is required explicitly —
a bare `#[napi]` does not register a constructor ([ADR-020]). Setters use
`#[napi(setter)]`, not `#[napi(set)]` ([ADR-021]).

**Interior mutability is required.** Returning a `Cell` by value means
`ws.getCell('A1').value = 42` mutates a temporary and is silently discarded — a failure
that compiles and looks correct. `Cell` holds `Arc<Mutex<CellInner>>` so the returned value
shares state with the worksheet. See [ADR-019].

**Enum variants the read path cannot populate are lies that type-check.** This is why
`Merge`, `RichText`, `Hyperlink`, and `SharedString` were removed rather than shipped empty
in v0.1. See [ADR-017].

**One variant gap is still open:** calamine's `DataTimeIso` and `DurationIso` have no
`CellValue` counterpart, so ISO-8601 date cells read back as plain strings rather than
`Date`. See [ADR-018].

## 4. Canonical style serialization

**These rules are load-bearing for output determinism, not style guidance.** ADR-027
dedups the style table through a `BTreeMap` keyed on each style's canonical serialized
form, so the key must be deterministic or the same workbook produces byte-different output
across runs. Changing any rule below changes emitted `cellXfs` indices.

- **Colors** (`Font.color`, `Fill.foreground`, `Fill.background`, `BorderStyle.color`) must
  match `^[0-9A-Fa-f]{6}([0-9A-Fa-f]{2})?$`. Invalid input is rejected with
  `ExcelrsError::InvalidStyle`. Valid input is uppercased before storage; the canonical form
  is uppercase ARGB or RGB.
- **Float fields** (`Font.size`) must be finite; `NaN` and `±Infinity` are rejected.
- **String fields** (`Font.name`, `Fill.pattern`) are preserved as given. `"calibri"` and
  `"Calibri"` are distinct dedup keys — Excel preserves case in font names.
- **`None` vs `Some("")`.** `None` is omitted from the canonical key. `Some("")` is a real
  value, distinct from `None`. Callers clear a field by explicitly setting `null`.
- **`Fill.kind`** must be `"none" | "solid" | "pattern" | "gradient"`. *(Corrected at
  v2.9.1: the previous text rejected `"gradient"`; gradient fills shipped in v0.12.0 and
  `FillKind::Gradient` is accepted — `src/model/style.rs:529`.)*
- **`BorderStyle.style`** must be one of `thin | medium | thick | dashed | dotted | double`.
  `"none"` is rejected; express "no top border" as `Border.top = None`.
- **`num_fmt`** must be `None` or a non-empty format-code string. `Some("")` is rejected —
  use `null` for no format. The code is otherwise passed through to OOXML unchanged.
- **Vertical alignment** is stored as `"middle"` (matching ExcelJS) and emitted as OOXML
  `vertical="center"`; the reader maps back. Other values pass through unchanged.
- **Default style.** A cell with no `Style` resolves to index 0, the built-in "Normal".
  `cell.style = null | undefined | {}` all resolve to Normal.
- **Style assignment is full-replace.** Assigning a style object replaces the style
  entirely; it is not a merge. To change one field, read the current style and spread it.

There are two dedup implementations that must agree: `build_style_table` (batch) and
`StyleAccumulator` (incremental, used by the streaming writer). The latter is documented as
producing byte-identical output to the former, and the streaming writer shares the
`SharedString` table and render logic with the in-memory path.

## 5. Build and release

Pointers, not procedure. The normative requirements live in the `release-verification` and
`platform-targets` capabilities; the workflow itself is `.github/workflows/release.yml`.

- **Build:** `pnpm build` (debug) / `pnpm build:release`. `scripts/apply-glue.cjs` installs
  the JS glue as a napi build pipe.
- **Test:** `pnpm test` (vitest, with `--expose-gc`), plus 470 Rust `#[test]`s in `src/`.
- **Lint/format:** `cargo clippy -- -D warnings`, `cargo fmt`, `biome lint`.
- **Release:** tag-driven on `main` ([ADR-007]); npm trusted publishing via OIDC, no stored
  token. The build matrix in `release.yml` and `package.json` `napi.targets` must agree —
  the `platform-targets` capability states that as an invariant rather than enumerating
  targets.
- **musl binaries link musl dynamically.** A fully statically linked musl addon segfaults
  on load, because it carries its own libc. This is the one platform constraint that
  survives in a capability as its own requirement, because it is knowledge rather than
  inventory.
