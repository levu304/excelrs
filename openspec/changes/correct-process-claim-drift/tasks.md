## 6. musl loading and load-failure diagnostics

- [x] 6.1 Invert the `platform-targets` requirement *musl binaries load without a host-matched libc*. It asserted that dynamic musl linkage lets the binary "load in any Node.js process regardless of the host's libc", with a scenario requiring a successful round-trip on a non-musl-glibc host. That is the opposite of what dynamic linkage provides: the cdylib records its musl libc as a dynamic dependency, so a glibc host cannot resolve it. Restate the requirement around what is actually true and enforced — dynamic linkage is mandatory because a fully static musl cdylib segfaults on `dlopen`, the binary loads on a musl host of the same architecture, and a non-musl host gets a loader error rather than a successful load or a crash. Verify by running `readelf -d` on the built musl binary and confirming the recorded `NEEDED` entry, loading it in a glibc container and confirming it fails naming the unresolved dependency, loading it in a matching-arch Alpine container and confirming it round-trips, and confirming the existing release assertion still rejects a fully static build.
- [x] 6.2 Make `scripts/streaming-smoke.cjs` report the load-failure cause chain. It printed only the first line of `err.message`, which `index.js` always sets to the `Cannot find native binding … npm has a bug related to optional dependencies` text, while the real reason survives only in the chained `err.cause`. Walk the chain so the failure names the artifact problem instead of sending the reader through npm. Verify by forcing a load failure with a foreign-architecture binary under `NAPI_RS_NATIVE_LIBRARY_PATH` and confirming the output contains the loader's relocation error and not only the npm message, and by confirming the normal pass path is unchanged.
