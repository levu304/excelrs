## Why

`Cell.value` currently returns a flat `CellValue` wrapper for every cell — `{ valueType: "Number", number: 42 }` for what users expect to be `42`. This is the single worst DX papercut in the API: reading a number requires `cell.value.number` (with a non-null assertion in TS), and `cell.value + 1` does not type-check or run. ExcelJS returns the actual JS primitive (`cell.value === 42`) and uses a separate `cell.type` discriminant, so excelrs diverges from the library it ports. This change brings `Cell.value` to ExcelJS parity and adds a proper `cell.type` accessor.

## Changes

- **BREAKING** `Cell.value` getter now returns the underlying JS primitive for simple cells:
  - `Number` → `number`
  - `String` → `string`
  - `Boolean` → `boolean`
  - `Date` → `Date` (via `JsDate.to_unknown()`)
  - `Null` → `null`
  - Rich cells (Formula, RichText, Hyperlink, Error, Merge) continue to return a `CellValue` object.
- **BREAKING** The TypeScript `CellValue` interface becomes a proper discriminated union (`CellValueResult`) so `cell.value` narrows correctly and rich-type shapes stay typed.
- **NEW** `Cell.type` getter returns a `CellType` string enum (`"Null" | "Number" | "String" | "Boolean" | "Date" | "Formula" | "Error" | "Hyperlink" | "RichText" | "Merge"`) — the discriminant that replaces `cell.value.valueType` checks on primitives.
- `Cell.date` getter is retained for backward compatibility (now redundant for Date cells since `cell.value` returns a `Date`); to be documented as deprecated for v3.
- `Row.addRow` / `Row.insertRow` already accept `Array<any>`, so no change there. `TableRow.values` keeps `Array<CellValue>` (table-specific data shape).

## Capabilities

### New Capabilities

- `cell-value-getter`: Defines the public `Cell.value` getter contract — return types for each cell-value variant (primitive vs. rich object), the new `Cell.type` discriminant accessor, and the `CellValueResult` TypeScript union. Supersedes the current flat-struct behavior.

### Modified Capabilities

- `cell-value-dispatch`: Setter dispatch behavior is unchanged, but the getter contract it pairs with changes from "returns `CellValue`" to "returns primitive for simple cells, `CellValue` for rich cells". The spec's current assumption that `cell.value` returns a `CellValue` with `value_type` must be relaxed.

## Impact

- **APIs**: `Cell.value` (getter) — **BREAKING**. `Cell.type` — NEW. `Cell.date` — retained, deprecation note added.
- **Code**: `src/model/cell.rs` (`value` getter, new `value_type`/`type` getter, `CellType` enum). `package.json` napi config (`dtsHeaderFile`). New `dts-header.d.ts` for union types + `Cell` declaration merge. `index.d.ts` / `native.d.ts` regenerated by build.
- **Tests**: `__test__/cell.test.ts`, `__test__/xlsx-async-contract.test.ts`, `__test__/rich-text.test.ts` update simple-type assertions from `cell.value.valueType` / `cell.value.number` to `cell.type` / `cell.value`. Rich-type tests unchanged.
- **Versioning**: Shipped as `v2.5.0` (minor bump, intentional breaking change — SemVer consumers on `^2.x` will auto-upgrade; documented in release notes).
- **Dependencies**: No new Rust or JS dependencies. Uses existing `napi-rs` `to_unknown()` (Path A, same `transmute` trick already in `date` getter) and `dtsHeaderFile` config.
