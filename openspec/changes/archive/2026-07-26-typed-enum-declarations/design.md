## Context

The auto-generated `index.d.ts` from napi-rs maps Rust `String` fields to TypeScript `string` with no further narrowing. For ~20 fields across the public API surface, the valid values are well-defined enumerations documented in doc comments and validated by Rust-side `validate()` functions, but TypeScript users get zero compile-time safety.

The `native.d.ts` is also auto-generated and mirrors the same issue — but `index.d.ts` re-exports/wraps these types, so fixing the TS surface in `index.d.ts` (or a companion) is sufficient for consumers of the npm package.

The constraint: `index.d.ts` carries the header `/* auto-generated by NAPI-RS */` and is overwritten on every `napi build`. Patching it directly creates a maintenance hazard. The project already has precedent for augmenting the auto-generated output: the `// __EXCELJS_GETCELL_GLUE__` section does declaration merging inline in `index.d.ts`, meaning the team accepts some manual patching of this file.

## Goals / Non-Goals

**Goals:**

- Every enum-like `String` field in the public API gets a TypeScript string literal union type
- Zero runtime behavior change — all values remain the same strings at JS runtime
- Autocomplete works in modern TS editors for all enum fields
- The fix survives `napi build` regeneration (either via regeneration-safe approach or CI check)

**Non-Goals:**

- Converting Rust struct fields to Rust `enum` types for their own sake (only where it improves the generated TS)
- JS API surface changes (no `FillKind.Solid` imports required)
- Changing Rust validation logic — the Rust side already validates these strings correctly
- `native.d.ts` manually (it's auto-generated; regenerated from Rust)

## Decisions

### Decision 1: Hybrid approach — Rust `string_enum` for simple cases, TS overlay for complex ones

**Chosen**: Split approach from proposal.

**Rationale**:

- **Rust `#[napi(string_enum)]`** for self-contained enums (`FillKind`, `BorderStyleStyle`, `AlignmentHorizontal`, `AlignmentVertical`, `GradientType`, `SheetViewState`, `ActivePane`, `AnchorType`, `Orientation`, `CellComments`) generates proper TS string literal unions in `index.d.ts`, requires no hand-maintained TS code, and survives regeneration naturally. These are simple enums with no variant data.
- **TS declaration overlay** (hand-written string literal unions in a companion file) for complex discriminators like `CellValue.valueType`, `CfRule.type`, `CfRule.operator`, `DataValidation.type`, `DataValidation.operator`. These are either flat-tag discriminants (Rust enums with variant data can't cross FFI) or are too large/consequential to risk Rust enum conversion. The overlay file merges with the auto-generated declarations.

**Alternatives considered**:

- *All-Rust enums*: Rejected because `CellValue.valueType` and many CfRule/DataValidation fields carry complex variant data or are flat-tag discriminators that don't map to simple Rust enums.
- *Post-generation script patching*: Rejected as fragile — a regex-based script that rewrites `index.d.ts` after each `napi build` would break silently on napi-rs output format changes.

### Decision 2: Companion declaration file (`enums.d.ts`) for overlay types

**Chosen**: Create `enums.d.ts` at package root with all TS string literal unions and module augmentation.

**Rationale**: Keeps the auto-generated `index.d.ts` untouched (except for the existing `__EXCELJS_GETCELL_GLUE__` section). TypeScript's declaration merging picks up the companion file automatically when it's in the same package. Published via `package.json` `"types"` field (already points to `index.d.ts` — TypeScript auto-includes sibling `.d.ts` files that aren't explicitly excluded).

The file structure:

```
enums.d.ts         — Hand-written: string literal type aliases + module augmentation
index.d.ts         — Auto-generated by napi-rs (no new manual changes)
native.d.ts        — Auto-generated by napi-rs (regenerated after Rust changes)
```

### Decision 3: Rust `string_enum` naming convention

**Chosen**: PascalCase enum variants in Rust map to camelCase string values that match current usage. E.g.:

```rust
#[napi(string_enum)]
pub enum FillKind {
    None,
    Solid,
    Pattern,
    Gradient,
}
```

This generates `"none" | "solid" | "pattern" | "gradient"` in TS — identical to current string values, no migration needed.

**Checked**: napi-rs v3 `string_enum` emits lowercase-first-letter variants matching the current literal values for the simple enums listed in Decision 1.

### Decision 5: CellValue.valueType — TS helper type, not enum

`CellValue` is a flat tagged union by design (the napi-rs v3 spike proved Rust enums with variant data can't cross FFI). The `value_type` string is the discriminator. We'll add a TS type alias:

```typescript
export type CellValueType = "Null" | "Number" | "String" | "Boolean" | "Formula" | "Error" | "Hyperlink" | "RichText" | "Merge" | "Date";
```

And augment `CellValue.valueType`'s declaration. This gives autocomplete without changing the Rust struct.

## Risks / Trade-offs

- **[Risk] Companion file not picked up by all consumers** → TypeScript auto-discovers sibling `.d.ts` files, but `package.json` `"types"` pointing only to `index.d.ts` may shadow it. **Mitigation**: Add `/// <reference path="./enums.d.ts" />` at the top of `index.d.ts`, or ensure `enums.d.ts` is imported/exported via the main type entry.
- **[Risk] Rust `string_enum` variant naming mismatch** → If napi-rs doesn't emit the exact lowercase string our code expects, the Rust side could break. **Mitigation**: Verify generated `index.d.ts` output matches expected strings after each Rust enum conversion.
- **[Risk] Regeneration overwrites `index.d.ts`** → The companion `enums.d.ts` approach means only the companion file is hand-maintained. `index.d.ts` gets Rust-enum-generated types for free. No hand-edits needed in `index.d.ts` beyond what already exists.
- **[Trade-off] Two sources of truth** → Rust `#[napi]` enums and TS-side type aliases both define valid value sets. They could drift if one is updated but not the other. Acceptable because: (a) Rust enums are compiled — a mismatch is a compile error; (b) TS overlay types can be checked by a test that reads the runtime value sets from the Rust side.

## Migration Plan

1. **Phase 1 — Rust `string_enum` conversions**: Convert simple enum fields (style, image, sheet view, page setup) to Rust `#[napi(string_enum)]` types. Regenerate `index.d.ts` and `native.d.ts` via `pnpm build:types` (or equivalent). Verify generated types match expected string literals.

2. **Phase 2 — TS overlay file**: Create `enums.d.ts` with string literal type aliases and module augmentation for the complex discriminators (CellValue.valueType, CfRule.*, DataValidation.*). Verify via `tsc --noEmit` on a consumer file.

3. **Phase 3 — Validation test**: Add a test that introspects runtime JS values of enum fields and compares against the TS type definitions, catching drift. (Can be done as a script, not a Rust test.)

4. **Rollback**: Remove `enums.d.ts` and revert Rust enum conversions. Regenerate `index.d.ts`.

## Open Questions

- Should `WorkbookView.visibility` be converted to Rust enum or handled in TS overlay? (Low priority — it's rarely used.)
- Does napi-rs v3 `string_enum` handle `""` (empty string) as a valid variant? Relevant for `SheetView.state` which can be `"frozen"`, `"split"`, or `""`. (If not, handle `""` via TS overlay.)
- Do existing consumers of the package that use `// @ts-ignore` or type assertions need migration support? (Probably not for TS-only changes — same JS values.)
