## Context

`Workbook.add_worksheet` currently takes a single `name: String` parameter and
returns a blank `Worksheet`. The worksheet model already has inner setters
(`set_views_inner`, `set_page_setup_inner`, `set_header_footer_inner`,
`set_protection_inner`, `set_auto_filter_inner`) used by the reader to
populate worksheet state after creation. These can be reused to apply an
options object at creation time.

`SheetView` currently models `{ state, xSplit, ySplit, topLeftCell,
activePane }` but omits `showGridLines` — a boolean attribute on the OOXML
`<sheetView>` element. The reader (`parse_views_from_xml`) and writer
(`emit_sheet_views`) both need updating to handle this attribute.

## Goals / Non-Goals

**Goals:**

- Allow `addWorksheet(name, options?)` where `options` carries page setup,
  views, header/footer, protection, and auto-filter — applied atomically
  before the worksheet is returned.
- Add `showGridLines` to `SheetView` model, reader, and writer.
- Zero breaking changes — existing single-arg callers unaffected.
- Match ExcelJS `AddWorksheetOptions` shape as closely as practical.

**Non-Goals:**

- Worksheet properties not supported by existing inner setters (tab color,
  outline level, sheet state — deferred).
- Validation of option values beyond what the existing setters already do.
- Performance optimization — napi-rs object deserialization cost is negligible
  for creation-time options.

## Decisions

### D1 — AddWorksheetOptions lives in workbook.rs alongside the napi impl

`AddWorksheetOptions` is a `#[napi(object)]` struct placed directly in
`src/model/workbook.rs` (same file as the `Workbook` napi impl). It is small,
tightly coupled to the `add_worksheet` binding, and has no independent reason
to live in its own file. A new file would be justified if the struct grew
significantly or was reused elsewhere — it isn't.

**Alternative considered:** placing it in `src/types.rs` — rejected because
it's workbook-domain, not a cross-cutting type. **Alternative:** a separate
`src/model/add_worksheet_options.rs` — rejected as over-splitting for a
struct with 5 optional fields.

### D2 — Options applied via existing inner setters, not inline field mutation

`WorkbookInner::add_worksheet` already creates a `Worksheet::new(name)` and
calls `ws.set_id(id)`. The options branch will call the same inner setters
(`set_views_inner`, `set_page_setup_inner`, …) that the reader uses. This
avoids duplicating the lock/unlock and set logic.

```
ws → set views_inner(v)  // same path reader uses
   → set page_setup_inner(ps)
   → set header_footer_inner(hf)
   → set protection_inner(p)
   → set_auto_filter_inner(af)
```

**Why not direct `*self.views.lock()`?** The inner setters already exist,
tested, and handle the lock. Calling them keeps the apply path consistent
with the reader apply path. **Why not apply in the `Workbook` napi layer?**
The inner lock is held in `WorkbookInner::add_worksheet` — applying there
avoids releasing and re-acquiring the mutex.

### D3 — napi-rs `Option<T>` maps naturally to optional JS arg

napi-rs treats `Option<AddWorksheetOptions>` as `options?: AddWorksheetOptions`
in the generated TS. No manual overload or wrapper needed. The existing
single-arg call continues to compile because `options` is `undefined` → Rust
receives `None`.

### D4 — showGridLines follows the existing SheetView attribute pattern

`showGridLines` is a `<sheetView>` attribute (not a `<pane>` child), parsed
in the same attribute match block as `state` and `topLeftCell`, emitted in
the same `format!` call as `state`. No structural changes to the reader/writer
loop — just one new attribute branch on each side.

## Risks / Trade-offs

| Risk | Mitigation |
| ------ | ------------ |
| Options struct grows stale as new worksheet properties are added | The `AddWorksheetOptions` struct is co-located with `Workbook` and easily extended; adding a new field is O(1) |
| `showGridLines` OOXML default is `true` — omitting the attribute is correct but non-obvious | Comment in the `SheetView` field and in the writer emission makes the default explicit |
| napi-rs may not emit `Optional<T>` for object fields exactly as hand-written TS | The `native.d.ts` is auto-generated by napi-rs and the hand-written `index.d.ts` may need a manual `?` check on `AddWorksheetOptions` interface fields |

## Migration Plan

1. Add `show_grid_lines: Option<bool>` to `SheetView` struct.
2. Parse `showGridLines` in `parse_views_from_xml`.
3. Emit `showGridLines` in `emit_sheet_views`.
4. Create `AddWorksheetOptions` napi-object struct in `workbook.rs`.
5. Modify `Workbook::add_worksheet` and `WorkbookInner::add_worksheet` to
   accept `Option<AddWorksheetOptions>` and apply via inner setters.
6. Update `index.d.ts`: new `AddWorksheetOptions` interface, new
   `addWorksheet` signature, `showGridLines` on `SheetView`.
7. Add tests: unit test for options application, round-trip test for
   `showGridLines`.
