# Design

## Context

See `proposal.md` — Why, for motivation. What constrains the approach:

The package publishes two type-declaration files. `native.d.ts` is generated by
`napi build --dts native.d.ts` and gitignored; `index.d.ts` is hand-maintained and is what
`package.json` `types` points at. `scripts/apply-glue.cjs` refines the generated file as a
`napi --pipe` hook and deliberately never touches the published one.

`scripts/verify-build-output.cjs` runs after the build in three places — `ci.yml:63`,
`release.yml:122`, and `pnpm verify:build` — and currently reads only the generated file.
Its header comment records a prior deliberate decision: it asserts the *presence of specific
transforms* rather than diffing the generated file against a committed copy, because a napi
version bump would otherwise turn every release into a diff to review.

Two measurements shape the approach:

- Comparing the two files' exported names with a regex reports **13 names missing** from
  `index.d.ts` that are in fact exported. Declarations in a `.d.ts` are exported without the
  `export` keyword, so any keyword-based parse is wrong. The TypeScript compiler API reports
  the truth: 67 exports each, with exactly one name generated-only.
- `enum` declaration form is a plain keyword difference, cheap to compare, and unchanged by a
  napi bump that does not alter the exported surface.

## Goals / Non-Goals

**Goals:**

- Make the published declarations importable by a consumer compiling with isolated modules.
- Close the one hole where a runtime export has no type declaration.
- Make published-vs-generated divergence fail the build, in the check that already runs.
- Remove the hand-maintained list of names in `index.js` rather than add a check for it.

**Non-Goals:**

- Not restating the exported surface in any spec or committed file. The requirement states
  coverage; the check computes it.
- Not changing any enum value, class shape, or runtime behavior.
- Not making `index.d.ts` a build output. See Decision 5.

## Decisions

### 1. Parse both declarations with the TypeScript compiler API, not with a regex

`typescript` is already a devDependency and is already installed in every job that runs the
check. A prototype measured both approaches on the current tree: the compiler API returned
the correct answer for both files in ~0.5s, while the regex reported thirteen false
positives — every enum plus `CellValueInput`, all of which are genuinely exported.

A keyword regex would fail CI on a correct `index.d.ts`, and the failure would look like a
real defect. That is worse than no check.

*Rejected:* a hand-maintained allowlist of "names the regex can't see." It reintroduces the
hand-maintained inventory this change exists to remove.

### 2. Assert one-directional coverage, not set equality

Every name the generated declarations export must also be declared in the published
declarations. The published file may declare additional names, because it legitimately
carries aliases the generated one does not — `WorksheetState` is one today and stays one.

*Rejected:* strict set equality. It would fail on every intentional alias, so the first
person to hit it would add an allowlist, and the allowlist would rot.

### 3. Extend `verify-build-output.cjs`; add no new script and change no pipeline

The check already requires `native.d.ts` to exist, already runs post-build in CI and
release, and already has three callers. A separate script would need wiring into all three
plus a new package script, and would duplicate the file-existence precondition.

### 4. Compare enum declaration form only, never whole-file text

This is compatible with the existing decision recorded in the script header rather than an
override of it. That decision rejected diffing the generated file against a committed *copy*.
Comparing the exported-name set and whether each enum is `const` is invariant to a napi bump
that does not change the surface, so it does not produce the churn the header warns about.

### 5. `WorksheetState` becomes a derived alias, not a restated union

Today `WorksheetState` is a hand-written union of the three literal values. Aliasing it to
the enum type instead — the obvious reading of "keep it as an alias" — **breaks consumers**.
Measured: with the alias pointing at the enum, `ws.state = 'visible'` and
`const s: WorksheetState = 'hidden'` both fail with `TS2322`, because string enum types do
not accept bare string literals. Today's union accepts both.

The alias is therefore written as a template literal type over the enum, ``` `${SheetState}` ```.
Measured: literal assignment and literal widening both still compile, and the three values are
no longer written out a second time, so the alias cannot drift from the enum.

### 6. Declare `SheetState`, and delete the redundant `index.js` re-export block

`SheetState` is exported at runtime and had no type declaration, so `import { SheetState }`
failed to compile while plain JavaScript worked. It is declared as a plain enum.

Separately, `index.js` assigns all 22 of its names one by one after `module.exports =
nativeBinding` has already published the whole binding object. Verified: every one of the 22
is already reachable, and none is a rename. The block is a pure no-op — a second
hand-maintained list of the same enum and class names, with nothing checking it. Per the
project's design rule to prefer deleting a place that can rot over adding a mechanism to check
it, the block is deleted rather than verified.

## Risks / Trade-offs

- **A napi bump that changes the exported surface now fails CI.** → The failure names the
  missing declaration and the fix is one line in a hand-maintained file. This friction is the
  intended prompt, but it is new: a routine dependency bump that previously passed silently
  will now stop. Acceptable, and preferable to shipping the divergence.
- **The template-literal alias requires TypeScript 4.1 or newer.** A consumer on an older
  compiler fails to parse the published declarations. TS 4.1 predates the package's own
  devDependency floor by years, so the exposure is small. If it ever matters, the fallback is
  the explicit union, at the cost of restating the values.
- **The check reads build output, so it cannot run before a build.** → Not a new constraint;
  the existing check in the same file already requires `native.d.ts` and reports a clear
  "was the native addon built?" message when it is absent.
- **Parsing adds roughly half a second and reads `typescript` at check time.** → Negligible
  against a build job, and `typescript` is already loaded by `pnpm typecheck` in the same job.
- **`WorksheetState` and `SheetState` now both name the same three values.** → Two names for
  one concept is mild surface duplication, accepted deliberately: `WorksheetState` is
  ExcelJS-compatible and removing it would break consumers. The derived form keeps them
  mechanically consistent.

## Migration Plan

Single change, no data migration, no runtime behavior change. Consumers see a widened type
surface: enums become importable under isolated modules, and `SheetState` gains a
declaration. Nothing is removed. Rollback is a revert of the commit.
